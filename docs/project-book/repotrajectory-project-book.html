Orientation / 01

Executive summary

RepoTrajectory is an explainable open-source repository intelligence system. It continuously builds a bounded evidence base and presents repository discovery, health, momentum, delivery, and contributor-dependency signals through a research console.

Backend
FastAPI

Async SQLAlchemy and durable jobs.

Frontend
Next.js

Server/client UI with typed fetch layer.

Store
PG16

Relational facts plus pgvector.

Sources
2

GitHub REST/Search + GH Archive.

Core idea

Separate cheap, wide discovery from expensive, narrow historical hydration. Search and GH Archive identify candidates; policy selects a cohort; workers hydrate only that bounded set; analytics store components and evidence alongside scores.

Primary outputs

  • Canonical repository directory with filters and lenses.
  • Hybrid lexical/semantic search.
  • Scout feed for under-the-radar promise.
  • Deep repository dossiers and comparison.
  • Collector observability and a hardened admin plane.

Key architectural properties

  • Idempotent upserts and unique job deduplication.
  • Leased PostgreSQL queue safe for multiple workers.
  • Bounded collection and explicit retention policies.
  • Missing evidence remains missing; score weights re-normalize where defined.
  • Hosted AI is optional: deterministic fallback preserves availability.
  • Only Caddy exposes a host port by default.
One-sentence model: evidence sources → compact candidates → transparent selection → bounded hydration → explainable scoring → v1/v2 APIs → Next.js research workflows.

Architecture / 01

System context

Inbound evidence

GitHub Search yields recent public software metadata. GitHub REST hydrates repository entities. GH Archive yields public event counts without retaining raw payloads. An OpenAI-compatible endpoint optionally provides embeddings and structured Scout evaluation.

Outbound behavior

Public users receive read-only research views and APIs. A local operator receives a separate authenticated command surface. RepoTrajectory issues only GET requests to GitHub and does not write back to repositories.

Trust boundary: GitHub, GH Archive, and the AI endpoint are external dependencies. Browser traffic reaches the application through Caddy; PostgreSQL and Redis remain unexposed on the host in the default Compose file.

Domain / 01

Domain model and membership tiers

Two related models coexist: the original collection/hydration model and the newer canonical catalog model. They are linked but must not be conflated.

Legacy collection track

RepositoryCandidate is a discovered row. Tier values:

  • candidate: known, not selected.
  • active: selected by collection policy for recurring hydration.
  • pinned: explicitly requested, highest priority.

Repository is the deeply hydrated normalized record.

Canonical catalog track (v2)

CatalogRepository unifies broad discovery and hydrated facts. Flags/tiers:

  • candidate: retained pool.
  • directory: selected public catalog.
  • deep: highest-value directory subset, preferably hydrated.

Scout, embeddings, provenance, and search documents attach here.

Stable identity

GitHub numeric github_id is the durable external identity; full_name can change on rename/transfer. The GitHub client follows redirects, and catalog/repository upserts store the canonical response identity.

Key linkage

RepositoryCandidate.repository_id  ── optional 1:1 ──▶ Repository.id
CatalogRepository.repository_id  ── optional 1:1 ──▶ Repository.id
CatalogRepository.github_id      ── parent key ─────▶ search / embedding / scout
Implementation caution. Some services are mature legacy collection paths and others are v2 canonical paths. A new feature should declare which universe it reads and how synchronization is maintained.
Collection / 01

End-to-end evidence pipeline

Wide and cheap

Discovery is designed for tens of thousands of repositories. Metadata and compressed hourly counters are sufficient to classify and prioritize without paying deep REST cost.

Narrow and expensive

Hydration is bounded by time windows and item limits. Only selected or pinned repositories receive commits, PRs, issues, releases, contributors, snapshots, and metrics.

Essential invariant: candidate selection can be replayed; deep evidence is incremental and idempotent; raw GH Archive event JSON is never persisted.

Collection / 03

GitHub Search discovery

Legacy daily language search

services/discovery.py builds per-language searches with default eligibility of at least 500 stars and a push within 180 days. Results become RepositoryCandidate rows and collection memberships.

Canonical sharded search

services/directory.py searches language × star-band × freshness shards, allowing low-star projects into the v2 pool. Default scheduled shards cover the first two configured languages and bands 0–10, 11–50, and 51–200.

Canonical upsert behavior

  • Conflict key: numeric GitHub ID.
  • Initial classification is software with 0.8 confidence for the sharded path.
  • Normalized topics are lowercased and underscores become hyphens.
  • Search document is inserted/updated in the same use case.
  • Observation timestamps distinguish discovery from last observation.

Search limits

GitHub Search has its own smaller rate bucket and result ceilings. The client preserves a configured reserve and scheduled queries use dedupe keys scoped by language and day.

language:{language} stars:{min}..{max} pushed:>={cutoff} fork:false

Default languages: Python, TypeScript, JavaScript, Go, Rust, Java
Why two paths? The legacy collection prioritizes established active software for deep analytics; canonical sharding broadens the directory and Scout funnel toward emerging projects.
Collection / 04

GH Archive streaming and projection

Each lagged hourly .json.gz object is streamed, parsed line-by-line, folded into bounded counters, and discarded.

Recognized events

  • WatchEvent → star
  • ForkEvent → fork
  • PushEvent → push
  • PullRequestEvent → collaboration
  • IssuesEvent → collaboration
  • ReleaseEvent → delivery

Selection behavior

Adoption and collaboration lead ranking. Push volume is capped as supporting evidence to prevent noisy push streams from dominating. At most 500 repositories per hour are retained by default.

Projection lifecycle

  1. Scheduler chooses six hours ending three hours behind wall clock.
  2. GhArchiveClient.read_hour streams compressed bytes and events.
  3. Projector returns counters plus event and byte totals.
  4. persist_gh_archive_hour maps external repositories to candidates and atomically replaces that hour’s rows.
  5. GhArchiveFile records status, counts, bytes, algorithm version, and errors.
Versioning invariant. Dedupe keys and file records contain GH_ARCHIVE_ALGORITHM_VERSION. A formula change must bump the version so the configured hours replay and old projections do not mix with new ones.

Primary code: backend/app/services/discovery.py • orchestration: backend/app/services/collector.py

Collection / 05

Transparent repository classification

Classification gates expensive hydration and makes rejection explainable. It uses repository metadata, not an opaque model.

Class familyExamples of signalsHydration
library, framework, developer_tool, softwarePackage/framework/tool/app terms, software topics, focused descriptions.Eligible when other guards pass.
learning_resourceAwesome lists, tutorials, interview material, courses, roadmaps.Withheld.
templateBoilerplate, starter, template signals.Withheld.
unclassifiedInsufficient metadata or ambiguity.May receive one-request probe, bounded per reconcile.

Decision outputs

RepositoryClassification carries the label, confidence, eligibility, and a human-readable rejection reason. Candidate rows persist each field so collection UIs and operators can inspect policy outcomes.

Probe path

Uncertain GH Archive discoveries often lack rich metadata. The reconciler returns a bounded list of candidate IDs; probe_repository fetches one repository record, reapplies classification, then queues another reconcile.

Known limitation: this is an intake heuristic, not semantic truth. False positives/negatives are expected. Manual pinning exists for edge cases, and reclassification is an explicit CLI/admin operation.
Collection / 06

Reconciliation and cohort selection

Legacy active cohort

reconcile_collection combines candidate metadata with recent external activity. Seven-day signal percentiles and popularity inform trend_score. Eligible software is ranked; up to collector_active_limit (250 default) becomes active. Pinned entries remain privileged.

Hydration consequence

New active candidates enqueue hydrate_repository. Existing active repositories become due after their next refresh. Queue priorities are recomputed from tier and trend score.

Canonical directory

reconcile_directory_and_cohort selects up to 10,000 eligible catalog rows by selection score, stars, and recency while capping any language at 25%. Empty slots are filled by the next-best entries.

Deep subset and pruning

Up to 500 directory rows become deep, preferring already-hydrated repositories. Nonmembers older than 90 days are pruned, and the total pool is capped at 50,000 by deleting lowest-score nonmembers.

legacy priority: pinned = 100
active hydration = 25 + min(70, round(trend_score))

canonical order: selection_score DESC, stars DESC, pushed_at DESC
deep preference: hydrated, then selection_score, then stars
Transactional intent: flags and memberships describe the current policy result; job deduplication prevents each reconcile from creating duplicate work for the same time bucket.

Collection / 08

Incremental synchronization and GitHub behavior

Per-resource state

repository_sync_states stores resource, time watermark, ETag, Last-Modified, last success/error, and next sync. Subsequent collection uses watermarks to stop pagination once known history is reached.

Idempotency

Repositories, commits, issues, PRs, releases, contributors, languages, and topics use conflict-aware inserts/updates or replacement semantics. A UTC-day snapshot is updated rather than duplicated.

Client mechanics

  • 30-second HTTP timeout and up to three retries.
  • Serial request lock per worker client.
  • Minimum request interval, default 0.15s.
  • Exponential retry for 429/5xx and secondary limits.
  • Primary rate reset is parsed and surfaced as a typed exception.
  • Redirects followed for rename/transfer.
  • Pagination follows Link headers and supports stop conditions.

Rate-budget behavior

The client tracks limit, remaining, used, reset_at, resource, and per-process request count. The worker persists it in collector_state. When the reserve is reached or GitHub returns exhaustion, the current job is rescheduled after reset rather than failed.

Scaling rule: additional workers improve parsing and database concurrency but cannot create GitHub quota. Observe budget and DB latency before scaling.
Queue / 01

Durable queue state machine

Claim protocol

A worker selects one due queued row ordered by priority, schedule, then ID with FOR UPDATE SKIP LOCKED. It writes worker ID, lock time, first start time, and increments attempts before execution.

Recovery protocol

Every scheduler tick requeues running jobs whose lease exceeds the configured 30-minute default. Transient failures receive backoff; terminal/exhausted jobs remain visible.

Concurrency protection: admin retry/cancel uses status-conditional updates so a UI action cannot overwrite a job claimed concurrently by a worker.

Analytics / 01

Analytics execution and stored explanation

calculate_metrics(session, repo, window_days=30) compares a current window with the immediately preceding equal window, then appends a MetricSnapshot.

Queries performed

  • Human vs known-bot commit authors.
  • PR creation and resolution/merge timestamps.
  • Issue creation and close timestamps.
  • Stable releases only.
  • Recent contributors or all-time fallback.
  • Repository snapshot history and freshness maxima.

Stored component groups

  • methodology_version: 3
  • momentum, health, concentration
  • velocity, responsiveness, community
  • freshness, growth
  • assessment, data_quality

Bot heuristic

Logins ending in [bot] and the explicit values dependabot, dependabot-preview, github-actions, and pre-commit-ci are automation. Bot commits are excluded from human momentum/health inputs but stored as volume and share.

Analytics / 02

Momentum score

Question: is development and community activity accelerating? Every component is clamped to 0–100.

ComponentTransformWeight
Star growth50 + 50·tanh(star_rate·4)25%
Contributor growth50 + 50·tanh(contributor_rate·3)20%
Commit acceleration50 + 50·tanh(ratio_change(current, previous))25%
PR accelerationSame acceleration transform20%
Release cadence100·(1−exp(−releases_per_month/2))10%

Ratio convention

ratio_change(current, previous):
  previous > 0  → (current − previous) / previous
  previous = 0 and current > 0 → +1.0
  both zero → 0.0

Baseline handling

Star and contributor growth use an actual snapshot at or before the start of the window. If none exists, both components are excluded and remaining weights re-normalize. If there is also no current commit, PR, or release evidence, momentum is explicitly forced to 0.

Do not reconstruct historical stars. GitHub REST returns current counts. Growth is valid only from observations collected over time.
Analytics / 03

Community health score

Question: is the community active, responsive, and able to ship? Scale features use diminishing returns so raw project size does not dominate.

ComponentTransformWeight
Active human contributors100·(1−exp(−contributors/12))20%
Issue resolution100·exp(−median_close_hours/(72·4)); missing → 015%
PR merge time100·exp(−median_merge_hours/(48·4)); missing → 015%
PR merge rateMerged / resolved PRs × 10020%
Stable release cadence100·(1−exp(−releases_per_month/2))10%
Recent human commits100·(1−exp(−commits_per_week/15))20%

Cycle-time cohorts are selected by resolved during the window, reducing recent-open cohort bias. Issue close time is not first-response time; PR merge time is not review latency. Acceptance rate can encode deliberate governance strictness, not only health.

Evidence visibility: the snapshot stores median hours plus merged, resolved-PR, and closed-issue sample sizes. A consumer should show those counts next to the score.
Analytics / 04

Concentration, velocity, and confidence

Contributor-dependency proxy

top_1_share = largest contributor count / total
top_3_share = three largest counts / total
HHI = Σ(each contributor share²)
risk = 100 × (0.45·top_1 + 0.25·top_3 + 0.30·HHI)
effective_contributors = 1 / HHI

Basis is recent human commits. If none exist, cumulative GitHub contribution counts are used and the basis is marked. This is not a literal bus factor: it does not know permissions, knowledge ownership, or succession.

Velocity payload

Current/previous commits and PRs, merged PRs, issues opened/closed, net issue flow, stable releases, per-week/month normalized rates, and automated commit volume/share.

Freshness payload

Last commit/release timestamps and days since each. Repository dossier and assessment use these to avoid presenting stale evidence as current.

Confidence score

min(100,
  25
  min(current evidence events, 150) / 150 × 50
  min(snapshot span days, window days) / window days × 25)

The 25-point base means “confidence” is a coarse coverage indicator, not statistical certainty. Sample sizes remain separate.

The catalog row also stores individual activity_score, popularity_score, freshness_score, and maintenance_score fields. Selection then applies a language diversity cap to prevent one ecosystem from consuming more than 25% of target slots, followed by a fill pass.

Current implementation nuance: some discovery upserts seed component/selection scores with constants or simplified values, while deep sync seeds stronger values. If revising selection quality, trace every writer of CatalogRepository.selection_score, not only calculate_selection_score.
Scout / 01

Scout promise scoring

Scout seeks promising active software with no minimum star threshold. It combines deterministic evidence (70%) and structured provider evaluation (30%).

Quantitative componentConstruction
Adoption acceleration20 base + 15/star event + 10/fork event + bounded log-star term.
Development cadence30 base + 3/push event + 5/PR event.
Freshness100 − 1.5 per day since push; missing 20.
Contributor breadth25 base + forks, PR events, issue events.
Release activity20 base + 35/release event.
Maintenance responsiveness50 base; deep merged/closed evidence can raise it.
quantitative = .25 adoption + .20 cadence + .15 freshness
             + .15 breadth + .10 releases + .15 maintenance
promise      = .70 quantitative + .30 provider_overall_score

Separate confidence accumulates evidence presence: description .20, language .15, license .15, ≥2 topics .15, any recent events .20, ≥5 stars .15; bounded to 0.20–1.00.

Guardrails exclude forks, archived projects, known non-software classifications, and projects inactive for more than 180 days. Assessments expire after seven days and retain provider/prompt identity plus evidence references.

Scout / 02

AI provider contract and graceful degradation

Abstract interface

AIProvider exposes embedding generation, structured Scout evaluation, availability, and model identity. ScoutAIEvaluation requires an overall score, breakdown, rationale, surfaced reason, facts, uncertainty, risks, model, and prompt version.

Hosted provider

OpenAIProvider uses the OpenAI-compatible base URL, bearer key, embedding endpoint, and chat-completions JSON response. Default base URL targets Google’s OpenAI-compatible Gemini endpoint.

Fallback provider

When no effective key exists or provider access fails in supported paths, deterministic heuristics generate embeddings/evaluation behavior. The v2 health route reports degraded status and semantic_available tells search consumers what ran.

Factory

get_ai_provider selects hosted behavior only when GEMINI_API_KEY or AI_API_KEY is configured; Gemini key wins.

Design consequence: the system remains usable without hosted AI. Lexical search, broad catalog, deep metrics, and deterministic Scout evidence continue. Never make core read availability depend on provider credentials.
Naming nuance: class/file names say OpenAI because the protocol is OpenAI-compatible; the configured default evaluation model is gemini-3.8-flash.
Search / 01

Hybrid search and reciprocal rank fusion

Lexical branch

Searches normalized catalog text across full name, name, owner, description, topics, language/license, and README document fields. Structured filters are applied in SQL.

Semantic branch

Normalizes query, consults query_embedding_cache, requests an embedding if needed, and ranks catalog vectors by pgvector distance.

Rank lists combine through weighted reciprocal rank fusion with default k=60. Pagination uses a URL-safe base64 encoding of an offset. Responses include interpreted filters, rationale, evidence freshness, and an explicit semantic-availability flag.

Cursor semantics: the cursor is opaque to clients but currently offset-based, not keyset-based. Large/mutating result sets can shift between pages; a future keyset migration would be an API behavior change.
API / 01

API architecture and conventions

Mounts

  • /health: process liveness.
  • /api/v1: legacy repositories, analytics, collection, admin.
  • /api/v2: canonical directory, profile, search, Scout, facets, health.
  • Via Caddy, prepend /backend.

Session and errors

Async session dependency is request-scoped. Missing repositories produce 404; invalid parameters produce FastAPI 422. Most read responses are Pydantic-shaped. Admin failures use 401/403/409 as appropriate.

Conventions

  • All timestamps are timezone-aware ISO 8601 externally.
  • Ranking and score ranges are 0–100; Scout confidence is 0–1.
  • v2 lists return envelopes with items, next_cursor, and total_count.
  • Frontend requests use cache: "no-store".
  • OpenAPI metadata advertises API version 0.2.0; Python package version is 0.1.0.
  • Global response headers deny framing and sniffing, restrict referrers/permissions, and constrain CSP frame/base behavior.

Client base resolution

ThreatControl

Deployment boundary: local defaults use loopback HTTP and ADMIN_SECURE_COOKIES=false. For HTTPS exposure, set secure cookies and exact HTTPS allowed origins; replace default database credentials and conduct a review of legacy v1 mutation routes.

Security / 02

Authentication and CSRF flow

Token payload

Session contains username, issue/expiry times, and CSRF value. It is base64-url encoded and HMAC authenticated. Decode verifies structure, signature with constant-time comparison, username, and expiration.

Rotation

./run.sh admin-password prompts without echo, hashes the new password, generates a new session-signing secret, writes .env mode 0600, and invalidates all earlier sessions.

Cookie settings: HttpOnly, SameSite=Strict, configured Secure flag, bounded Max-Age. Admin responses receive Cache-Control: no-store.

Deployment / 01

Docker, startup, and proxy behavior

Startup order

  1. PostgreSQL and Redis reach health.
  2. API runs alembic upgrade head, then Uvicorn.
  3. Collector waits for healthy API.
  4. Web depends on API health.
  5. Caddy routes after web/API exist.

Network segmentation

All services join internal; application services needing outbound access also join public. Only proxy publishes a host port. Database and API use Compose expose, not host ports.

Caddy route contract

:80 {
  handle_path /backend/* { reverse_proxy api:8000 }
  handle { reverse_proxy web:3000 }
}

Persistence

postgres_data holds the database, backups_data holds backup files, redis_data holds Redis state, and Caddy has data/config volumes. Stopping containers is recoverable; deleting volumes is destructive.

Production hardening: local database credentials are embedded in Compose for convenience. A public deployment needs external secret management, TLS, exact origins, secure cookies, monitoring, backup scheduling, and explicit network/firewall policy.

Operations / 02

Backup, restore, and disaster recovery

Backup script

scripts/backup.sh produces timestamped compressed custom-format pg_dump files in /backups/daily. Sundays are copied to weekly.

  • Daily retention: 7 days.
  • Weekly retention: 28 days.
  • Defaults target Compose PostgreSQL.

Restore script

scripts/restore.sh accepts a backup and optional --rehearsal. Rehearsal creates an isolated database, restores, checks key table counts, and drops it.

  • --clean --if-exists.
  • --no-owner --no-acl.
  • Verifies catalog/repo/embedding/scout counts.

Recovery objectives by data class

DataRecoverability
GitHub entitiesReplayable within current API availability and configured bounds.
GH Archive compact hoursReplayable from public archive; algorithm version controls replacement.
Observed historical snapshotsNot reconstructable exactly after loss; backups matter.
Job/audit historyOperational evidence; not fully recreated from sources.
Embeddings/ScoutRegenerable if provider/config remains available.
Restore-script caveat: pg_restore … || true can mask restore errors. A production recovery procedure should inspect command status/logs and validate more than four counts before declaring success.
